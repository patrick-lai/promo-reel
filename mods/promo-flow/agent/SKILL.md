# promo-flow mod: publishing contract
The person sees and decides in the Stage pane; you do the work with `promo flow` (see the promo-reel skill, THE FLOW).

**Starting.** The pane must be open before you do anything else: `commissionctl mod activate promo-flow` (idempotent; it shows "Preparing…" and the chat card at once, and a first publish replaces it). If the person typed `/promo-flow <request>` or clearly asked for a produced video (promo, hero, demo, trailer), go ahead. Otherwise ask first with the ask
widget ("Use the promo flow for this?") and start only on yes. Then `promo flow init <name> --intent "<their words, exact>"` and publish. The project folder comes from the person's save location (`promo config output`, the folder button in the Stage), not from the repo you are working in; never `cd` into the repo to scaffold or write project files there.

**Every change publishes itself.** Inside a CommissionAI thread every `promo flow` command that changes the flow (init, discover, script, doc, story, scene, council, approve, advance, asset, frames, make, draft, round, final, revise, note, share, resume, check, pin, restore, ab, autopilot, assume, lessons and the rest) writes `flow/state.json`, runs `commissionctl mod publish promo-flow` on it and prints `Stage updated`. If it prints `the Stage was not updated`, the flow change stands but the person does not see it: read the reason, fix it, then `promo flow publish`. If the host names a file it could not copy, that file is missing from the Stage: fix it (reshoot, re-encode, re-make) and `promo flow publish`.
Never edit the state JSON by hand (`promo flow snapshot --out F` prints it for a look). The first publish activates the mod in this thread. `summary` drives the chat card; `gate` is what the person is being asked.

**The gate IS the question; then the turn ends.** Once a state with a `gate` (or a `summary.badge` of `waiting`) is published, say in one line what you are waiting for, offer `commissionctl next --status needs_you ...`, and END THE TURN. Their click arrives as your next message. Never call AskUserQuestion, never `commissionctl ask` the same thing, never sleep, poll `mod status`, or loop waiting for an answer: a blocked tool call holds this thread, so the `[mod:promo-flow]` message cannot be delivered (one flow stalled six hours this way). While sub-agents run in the background, do other work or end the turn.

**Their clicks arrive as chat messages** starting `[mod:promo-flow]`:
- `approved <gate>` or `picked scripts A B`: run the exact `promo flow approve ... --by "NAME"` the message names (NAME is the person), then `promo flow advance` (each publishes).
  An answer one stage early (the pick while the flow is still at `scripts`) is fine: `approve` walks the flow forward when the checks pass. If it refuses, do what it lists as open, then approve again.
- `wants the real thing made, not placeholders: <what>`: run `promo flow make` (storyboard frames as real images, then a sample of every asset: concept still, short clip, audio excerpt), publish. If a sample fails (no source file for the music, no generator logged in), say exactly what is missing instead of publishing a placeholder.
- `chose where new videos are saved: <where>`: run the exact `promo config output "<where>"` the message names, then publish. It only changes where NEW videos go; never move the current one. If it refuses (drive not plugged in, bad path), say why in one sentence and publish nothing new.
- `asked for changes on <stage>: <text>` (also "Style: ..." from the discover step): do the work, regenerate what changed, `promo flow board`, publish. Do not approve.
  A "Style: X. Reference: URL" message is `promo flow discover --style "X" --ref URL`; "Style: X. No reference link." is `promo flow discover --style "X" --no-refs`; then `promo flow advance`.
- `sent draft feedback (round n of 5): <text>`: `promo flow round start --feedback "<text verbatim>"`, council, one batch, one draft, `round close`, publish. The Stage asks "Approve / Feedback and iterate" as soon as a draft is registered, still at the `drafts` stage: `round start` and `approve draft-approved` both move the flow into `review` themselves, so do not wait for an `advance` before acting on the answer.
- `asked for changes on review: <text>` once all 5 rounds are used (the Stage's "Restate direction"): `promo flow revise --feedback "<text verbatim>"` opens a new cycle with its own rounds; then the same council protocol, publish. `round start` refuses at the cap and says so.

- `wants <item> uploaded to <destination>`: the person clicked Upload on a draft or the final. The Stage only offers it where their `twg` is signed in and the product is there (`promo flow share detect` refreshes that, e.g. after they sign in). Run the exact `promo flow share draft|final N --to artifacts|loom --by "NAME"` from the message, then publish. It is private to them; widen with `--access open` only when they ask.
  Names are canonical: draft N is `<project>_draft_N` (edited and shared again, Artifacts refreshes the same link; Loom cannot replace, so it adds a copy and keeps the old links in the record), a final is `<project>_final_vN` (each `final add` is the next version and is never overwritten). Tell them the link it printed. If it fails, say the reason; an error that says to check Artifacts or Loom may have landed, so do not retry blindly.
  Never upload on your own (rule 5).
- `asked you to add to the plan (looking at the <tab> tab): <text>`: the person wants content in the Stage, in whatever size they ask for. Do it, then publish; do not approve. With several picked stories, do it for each (ids end in the story letter, e.g. `shotlist-a`) unless they named one. Pick the command from what they asked:
  - "the full script" / a longer script: `promo flow doc add full-script-a --kind script --title "Full script: <title>" --story A --file -` (pipe the text in; write a very long script in parts with `doc append` or `script append A --file -`). Any length is fine: the Stage paginates by `<!-- page: Title -->` markers, else by headings and length, with a contents list and find. Use markdown: headings, **Picture:** / **Voice:** / **Sound:** lines, tables, `- [ ]` checklists.
  - a shot list, edit plan, audio plan, capture checklist, claims, deliverables, schedule, treatment, director's notes: `promo flow doc new <kind> [--story A]` builds it from the real board and asset plan; then refine it (`doc add <kind> --force --file -`) so it is complete, not a template with holes.
  - "everything you need to direct / storyboard / workshop / edit": `promo flow plan pack` (the nine documents above, per story), then fill every `*( ... )*` hole and tell them what you assumed. `promo flow doc templates` lists the kinds; `doc list`, `doc rm ID` manage them.
  - something no fixed tab shows (a Blender render queue, a 3D model, a table of takes, a grade comparison): build a **widget**, a panel whose content you decide (below).
  - changes to the storyboard itself: `promo flow story`, `scene add|set|rm|list` (no hand-edited JSON; `--redraw start|end|mid|all` re-makes a frame), then `promo flow frames` for new pictures. The plan approval (storyboard + assets) goes stale on purpose when the board or what is planned changes: say so.
  - "more detail" / "frames every 5 seconds": `promo flow density --every 5 [--story A] [--scene 03]` (or `--clear`), then `promo flow frames` to draw them.
  Everything you write must be true to the footage (rule 3); put evidence in `proof` or the claims document.
- `commented on scene S of story X (...)`: `promo flow scene note X S --text "<their words>" --by NAME`, then change the scene to answer it (`scene set`, `--redraw`, `frames`),
  `promo flow scene resolve X S --note N --text "what you changed"` and publish. The storyboard cannot be approved while a comment is open.
- `sent you a message from the panel "<title>" (<id>): <text>`: the person pressed Send on a widget's bar. Treat it as their request about that panel or the video: change the widget (`widget add ID --force`, `widget layout`) or the flow, then publish. Do not approve anything.
- `changed N note(s) on the timeline of draft N: (1) ...`: one `promo flow pin add|edit|remove` per numbered change, their words verbatim; each note is a
  check on its scene for the next round. `answered the blind pick ...`: `promo flow ab pick`. `wants something else than your choice ...`: `promo flow assume overturn ID --text "<their words>"`.
  `asked you to forget a remembered note`: `promo flow lessons --forget ID`. `wants to go back to ...`: `promo flow restore --draft N [--scene ID] --by NAME`, rebuild
  what changed, register the new draft. Each publishes; none approves anything.
- `asked you to start working on your own (up to N)`: `promo flow autopilot start --minutes N --by NAME`, then loop: `autopilot pass begin`, one internal pass
  (council on the round brief, one batch, build, `draft add --report`, marks, `ab drafts` + judges), `autopilot pass end`, until it says done, blocked or out of
  time (after two passes that fixed nothing it asks for `autopilot replan --note` once). Choices you make without asking go on cards: `promo flow assume add`.
  `asked you to stop working on your own`: finish the pass you are in, `promo flow autopilot stop --by NAME`, show the latest draft.
- `wants storyboard frames <what> for story <S>`: `promo flow density --story S --every N` (N = 0 means `--clear`), then `promo flow frames`, publish. The Storyboard tab's cadence buttons send this; its Frames in time view shows every frame in time order.

**Widgets: panels you build when the fixed tabs fall short.** The Stage has fixed tabs (scripts, storyboard, assets, plan, drafts); when the job needs something they do not show, put a panel in the Stage instead of describing it in chat. `widget example blocks|html` prints a starter.
- Content you can state as data: `promo flow widget add render-queue --title "Blender render queue" --span 12 --file - --attach turntable.png=/abs/frame.png` with JSON on stdin: `{"blocks": [{"type": "stats", "items": [{"label": "Frames", "value": "240"}]}, {"type": "table", "columns": [...], "rows": [[...]]}, {"type": "image", "file": "turntable.png"}]}`. Block types: text (markdown), callout (tone info|ok|warn|bad), stats, kv, list, checklist, table, bars, progress, code, image, video, audio, gallery. The Stage draws them in its own style, so they match the theme and read well at 380 px.
- Anything else (a 3D viewer, a scrubber, a chart): `--kind html` with a self-contained HTML/CSS/JS fragment (stdin), run in a sandboxed frame with **no network** (inline libraries, attach files with `--attach NAME=PATH`). In the script: `promo.ready(() => ...)`, `promo.data["model.obj"]` (attached text), `await promo.file("still.png")` (a Blob), `promo.theme.accent`, CSS variables `--pf-ink --pf-dim --pf-well --pf-raised --pf-line --pf-accent`, and `promo.tell("text")`, which shows a bar with a Send button (the click comes back as a panel message). For 3D, render stills or a turntable with Blender and attach them, or export `.obj` / `.gltf` text.
- Layout is yours: `--place workbench` (default, its own tab; keep interactive widgets here) or `scripts|storyboard|assets|plan|draft` (pinned at the top of that tab); `--span 1-12` of a 12 column grid (8 + 4 side by side, 12 full row; narrow panes stack), `--height s|m|l|xl|auto`, `--order N`. `promo flow widget layout ID --span 6 --order 2` moves one; `widget list`, `widget rm ID`; `widget add ID --force` replaces the content and keeps its layout.
- Inside CommissionAI with native widgets (`commissionctl widget --help` works), every `--place workbench` widget goes to CommissionAI's Workbench tab instead of the mod; pinned widgets stay in the mod's tabs. A Send from a native panel arrives as `[widget:ID] ... sent this from the panel "TITLE": ...`: treat it like the mod's panel message. Keep writing `promo.*` and `--pf-*`; the native frame aliases them.
- Update a widget as the work moves (`widget add render-queue --force --file -`). Everything shown follows rule 3: only what the footage or the real run shows; a widget is never the product's UI (rule 1), and generated or demo content says so in its text. The Stage cannot tell you a widget looks wrong, so say in your reply what you put where.

**Before you ask for a decision**, `promo flow make`: the person decides by looking and listening, so every frame must be an image and every asset needs its real file or a sample. A text slate or an empty MOCK tile is not a preview, and the Approve button stays disabled while any exist.

**While you work (anything over ~2 minutes: captures, renders, voices, builds).** The person is waiting and cannot see your tools. Every ~3 minutes, and at each new sub-step:
`promo flow note "Rendering screenshots for scene 4" --kind render` (kinds: capture | render | voice | music | check | plan | other; add `--done` when that sub-step is finished); it publishes itself.
Write it as plain words about the video ("Taking snapshots of the real app"), never a command or a path. `promo flow make` notes itself.
`promo flow frames`, `make`, `asset make` and `promo build` / `promo shot` publish the state themselves after every picture, sample or build step, with a heartbeat every minute, so no notes are needed while they run.
A run killed half way shows as stopped with a "carry on" button. Its message is `wants the stopped run carried on (...). Run: <command>`: run that command (it only makes what is missing or changed), then publish.

**One question, one place.** The pane's `gate` is the question (style, scripts to pick, storyboard, assets, go, draft). While this mod is open, never put the same decision in the chat ask box (`status --json` says `ask_in_stage: true`): nothing closes it when they answer in the pane. Use the chat ask only for what the pane cannot carry (references and must-not-claim before there is a gate, a clarifying question). If a pane answer arrives while a chat question on the same gate is open, act on the pane answer and do not ask again.

**Never approve yourself** (an agent name is refused). Never send an action for them. `commissionctl mod status promo-flow` is for after a restart (what did they click while you were away); it is not something to poll.

At Keyframes, YOU record the real recordings and screenshots (rule 1: real footage only); never ask the person to record or send files. Drive the real app or its demo mode with the capture contract (`capture/README.md`: headless browser, DPR 2, locked framing, each take registered with `promo footage add`), post `promo flow note "Recording scene 3" --kind capture` as you go, and register each take with `promo flow asset add --force --source real --path FILE --how "..."`. While any are still `mock` or `todo` the Stage reads "Recording N clips from the real app" with the badge With the agent. The person can also add their own footage or pictures on the Stage's **Add files** tab (drag and drop or Finder). It arrives as a chat message starting `[mod:promo-flow] The person added N files from the Stage (attached)...`, the files under `.commission/attachments/`: copy them into the project's footage folder (they are not kept for long), register real footage with `promo footage add` / `promo flow asset add --force --source real --path FILE --how "..."`, look at it, say what it is, then publish. Never approve for them. Only if the product cannot be run here (no app, no login, no demo mode) say so with one `commissionctl ask` naming exactly what you are missing; recording itself is never the person's job.
